# Threat Model: Trawl

## 1. System context

Trawl is a Go 1.26/Kubebuilder Kubernetes operator for passive network-security monitoring in a trusted, single-organization Talos homelab. Operators create `NetworkTap` resources in a dedicated system namespace; the controller renders host-network Suricata and Zeek sensor workloads, an unprivileged Go sidecar normalizes analyzer logs and reports health, and a separate event worker converts Hubble Relay flow events. Traffic-derived observations leave pods through stdout for an externally deployed Alloy/Loki/Grafana stack. The manager also implements a synchronous, write-once S3/MinIO audit foundation for `NetworkTap` admission.

The currently reachable attack surface is `NetworkTap` admission and reconciliation, privileged analyzer pods, detection-content fetching, log normalization and status reporting, Hubble ingestion, configuration and mounted secrets, telemetry delivery, and audit storage. Accepted design documents also describe `CaptureJob`, `CapturePolicy`, PCAP persistence, an authorization gateway, and traffic decryption, but those are not currently reachable: `capture-runner` is a fail-loud stub, the related APIs and services remain unfinished tasks, and the owner confirmed that decryption is planned rather than implemented. Threats to those future features are therefore tracked as open questions rather than current runtime threats.

## 5. Deprioritized

| threat | reason |
|---|---|
| Direct anonymous internet attack on the Kubernetes or webhook API | The deployment is explicitly a non-internet-facing trusted homelab. Hostile packet content remains in scope through EP-03, but a public control API is not assumed. |
| PCAP gateway authorization bypass, presigned-URL theft, CaptureJob abuse, or retention races | These are important planned threats, but CaptureJob, CapturePolicy, the artifact gateway, and real capture persistence are not implemented or reachable. They must be modeled before those features ship. |
| Planned traffic-decryption key theft, plaintext disclosure, parser expansion, or unsafe failure behavior | Decryption is planned rather than implemented. The owner requires a dedicated threat review covering key custody, plaintext lifetime and destinations, added parser surfaces, authorization, and fail-open behavior before implementation. |
| T15 malicious user-provided Zeek script | Risk accepted by the owner: "we can't be responsible for user generated content at the end of the day, we can attempt to migtigate and warn but no promises can be made if you are using zeek script and pull in a malicious script." |
| EP-07 Hubble Relay stream: compromise or outage of Hubble itself | The owner assigns Hubble integrity and availability to the external platform administrator. Trawl remains responsible for truthful connection, loss, overlap, and degradation reporting. |
| General Kubernetes or Loki capacity exhaustion | The owner assigns base cluster and observability capacity to cluster administrators. Trawl remains responsible for bounded parsing, backpressure, per-source isolation, and complete loss accounting under T9. |
| EP-11 Alloy/Loki observation pipeline: authorization of observability users | The owner assigns least-privilege access grants to the administrator. Trawl remains responsible for data minimization and avoiding secrets or payloads in emitted records. |
| EP-14 Teardown and migration: residual credential and storage access | The owner assigns credential rotation, retained storage access, and lifecycle cleanup to the administrator. |
| SQL injection or database query tampering | No relational database or raw-query surface exists in the implemented system. |
| Browser CSRF or XSS against a Trawl UI | Trawl has no implemented browser UI. Grafana is external and exposes no current Trawl mutation action. |
| Cross-tenant privacy failure between adversarial organizations | Adversarial multitenancy is explicitly out of scope, though least privilege between workloads and operators remains in scope. |
| Repudiation of ordinary NetworkTap API mutations | The webhook derives the actor from the API-server request and commits before admission. Residual direct-webhook spoofing is captured as T12. |
| Inline credentials in Trawl configuration | Implemented configuration stores mount paths rather than secret values. Theft through workload or Kubernetes access remains covered by T1. |

## 6. Open questions

- [Owner-states] An attacker on the cluster network is a realistic actor for manager or webhook compromise. Affects: T1 actor and likelihood. Verify by: document actual manager, webhook, metrics, and probe reachability and test installed ingress policy.
- [Owner-states] Authenticated users with `NetworkTap` write access are in scope as potentially malicious or compromised actors. Affects: T2 actor and likelihood. Verify by: inventory production RBAC bindings for `networktaps`, `trawl-config`, workloads, RBAC, and NetworkPolicies in `trawl-system`.
- [Owner-states] Hostile monitored traffic is a first-class parser-compromise input, and traffic decryption is planned but not implemented. Affects: T3 applicability and the planned-decryption deprioritization. Verify by: inspect deployed analyzer versions and capabilities, and require a new threat-model pass before decryption code or keys ship.
- [Owner-states] Software and upstream-content supply-chain compromise are plausible. Affects: T4 and T7 applicability. Verify by: produce a complete inventory of mutable build, package, feed, repository, and registry inputs and their signature-verification state.
- [Owner-states] Production storage semantics and NetworkPolicy drift are relevant risks. Affects: T5 and T6 likelihood and status. Verify by: test the actual cluster for TLS, separate IAM, conditional writes, object lock, retention, denied lateral paths, and required Hubble, API, and storage paths.
- [Owner-states] Observation poisoning is plausible enough to retain as `possible`. Affects: T8 likelihood. Verify by: add adversarial parser and schema-drift tests and review rejection and correlation telemetry in a representative deployment.
- [Owner-states] General Kubernetes and Loki capacity are administrator responsibilities, while Trawl owns bounded work, backpressure, isolation, and loss accounting. Affects: T9 scope and status. Verify by: define application-level overload SLOs and run a separate capacity review against the selected defaults.
- [Owner-states] A compromised sensor rewriting its tap's complete status is applicable. Affects: T10 applicability. Verify by: review server-side-apply field ownership and test whether one sensor can alter another target entry.
- [Owner-states] Hubble integrity and availability, observability-user authorization, and residual storage or credential lifecycle are external administrator responsibilities. Affects: removal of T11, T13, and T14 from the active threat table. Verify by: record these ownership boundaries in operator documentation and production runbooks.
- [Owner-states] Client mTLS for the admission webhook is planned but is not a current control. Affects: T12 status. Verify by: inspect the deployed webhook TLS configuration and update T12 only after client identity and API-server-path restrictions are tested.
- [Owner-states] The execution risk of user-provided Zeek scripts is accepted, with Trawl responsible only for warnings, digest pinning, syntax checks, and feasible isolation. Affects: T15 status. Verify by: add and review explicit product documentation, admission warnings, and isolation tests for custom content.
- [Owner-states] Planned PCAP capture, artifact delivery, and traffic decryption remain outside the current runtime scope. Affects: section 5 deprioritization. Verify by: repeat threat modeling before those features become deployable.

## 8. Recommended mitigations

| mitigation | threat_ids | closes_class | effort |
|---|---|---|---|
| Narrow the installed RBAC first, split admission and audit from reconciliation where practical, and unmount credentials from processes that do not need them | T1,T2 | partial | M |
| Separate raw-socket capture from protocol parsing so native protocol decoders run with substantially less privilege | T3 | partial | L |
| Sign release images and analyzer content, verify provenance before use, and pin remaining mutable build and feed inputs where signing is not yet practical | T4,T7 | partial | M |
| Continuously test production storage semantics and installed network policy, including object lock, IAM, denied lateral paths, and every required service path | T5,T6 | partial | M |
| Add cross-parser property and fuzz tests, strict field bounds, source provenance, quarantine controls, and alerts on rejection or schema-drift rates | T8 | partial | M |
| Implement explicit backpressure and per-source quotas with bounded queues, per-tap isolation, and complete loss accounting | T9 | partial | L |
| Make the controller the sole aggregate NetworkTap status writer and validate scoped per-pod heartbeats against pod UID and ownership | T10 | yes | M |
| Restrict webhook ingress to the API-server path and complete planned client mTLS before treating direct AdmissionReview spoofing as mitigated | T12 | yes | M |
| Warn prominently that custom scripts execute within the analyzer trust boundary, require digest pinning and syntax checks, and isolate them as far as Zeek permits | T15 | partial | S |
